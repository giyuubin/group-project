본 프로젝트는 **Windows 실행 파일(.exe)의 PE(Portable Executable) 구조 내에서 파일을 직접 실행하지 않고 API 호출 패턴을 정적으로 추출하여 악성 여부를 사전 판별하는 초경량 1차 방어선(Pre-filter)** 구축을 목표로 합니다. 전체 시스템 구축 과정은 데이터 수집부터 최종 웹 데모 도구 개발까지 논리적인 파이프라인으로 구성되어 있으며, 각 단계별 상세한 진행 과정은 다음과 같습니다.

### 1단계: 데이터 수집 및 전처리 (Data Collection & Preprocessing)
*   **데이터 출처:** Kaggle 플랫폼에 공개된 Angelo Oliveira의 "Malware Analysis Datasets: Top-1000 PE Imports" 데이터셋을 활용했습니다. 이 데이터는 수만 개의 바이너리에서 가장 빈번하게 호출되는 상위 1,000개의 윈도우 API를 추출해 둔 고품질 데이터입니다.
*   **특징 및 구성:** 파일을 실행하지 않고 운영체제 커널 기능 호출 이정표인 IAT(Import Address Table)를 파싱하여, 특정 API를 호출하면 1, 아니면 0으로 기록된 희소 행렬(Sparse Matrix) 형태의 이진 피처(Binary Feature) 구조를 갖추고 있습니다. 총 47,580개의 샘플(결측치 없음)로 구성되며, 이 중 정상 파일은 1,929개, 악성 파일은 45,651개로 **약 1:23.7의 심각한 클래스 불균형**을 보입니다. 
*   **전처리:** `src/phase1_preprocess.py` 코드를 통해 데이터에서 불필요한 hash 식별자를 제거하고 결측값을 점검하여 분석을 위한 초기 준비를 완료했습니다.

### 2단계: 피처 엔지니어링 및 선택 (Feature Engineering & Selection)
초기 1,000개의 API 피처를 모두 사용하는 것은 모델의 과적합을 유발하고 추론 속도를 늦춰 '초경량 탐지'라는 기획 의도에 위배되므로, 실험을 통해 최적의 피처 개수를 찾아냈습니다.
*   **5-fold 격자 실험 (Grid Search):** 피처 개수(5~100개)와 리샘플링 비율을 교차하여 반복 학습하며 최적점을 탐색했습니다. 
*   **결과 (Top 50 채택):** LightGBM Gain Importance 기준으로 피처를 평가한 결과, 피처를 50개 이상으로 늘려도 성능 향상(Balanced Accuracy)이 정체되는 수확 체감(Diminishing returns) 현상을 확인했습니다. 이에 따라 추론 비용과 과적합 방지를 종합적으로 고려하여 상위 50개의 API만을 최종 피처로 확정했습니다. 이 상위 50개에는 `VirtualAlloc`, `Sleep` 등 악성 행위 관련 API와 `_cexit` 같은 정상 프로그램 종료 API가 명확히 분포해 있습니다.

### 3단계: 클래스 불균형 처리 (Handling Data Imbalance)
정상 표본이 극히 적은(1:23.7) 분포에서는 모델이 모든 파일을 악성으로만 예측하도록 편향되어 오탐(False Positive) 문제가 심각해집니다. 
*   **SMOTE 1:4 도입:** 정상 파일을 합성하여 균형을 맞추는 오버샘플링을 적용했습니다. 실험 결과, 원본 1:23 비율에서 **1:4 (정상:악성)** 비율로 맞췄을 때 Balanced Accuracy가 급격히 향상(+0.133)되었으며, 악성 파일을 놓치지 않는 지표(악성 Recall)도 0.973으로 높게 유지되었습니다. 정상 데이터를 원본의 약 3배(약 6,000개) 수준까지만 합성하므로 데이터 무결성 부담도 적어 이를 최종 채택했습니다.
*   **SMOTE-ENN 배제:** 결정 경계 노이즈를 제거하는 ENN 기법을 혼합해 보았으나, ENN 알고리즘이 SMOTE로 합성된 유효한 정상 샘플들까지 노이즈로 오인하여 삭제해버리는 부작용이 발생하여 채택하지 않았습니다.

### 4단계: 모델 선정 및 튜닝 (Model Selection & Tuning)
피처(50개)와 리샘플링(SMOTE 1:4) 전략이 확정된 후, 트리 기반 3종 모델(RandomForest, LightGBM, XGBoost)을 대상으로 교차 검증을 수행했습니다.
*   **LightGBM 채택:** 성능 자체는 세 모델이 통계적으로 동률이었습니다. 하지만 트리 모델이 가벼워 **실시간(ms 단위) 분류와 빠른 추론 속도**에 유리하며, 가장 중요한 오탐 최소화와 직결된 '정상 Recall(0.8341)' 지표가 3개 모델 중 가장 우수하다는 근거로 LightGBM을 최종 선택했습니다.
*   **하이퍼파라미터 튜닝:** `RandomizedSearch`를 통해 20회 탐색을 진행하여 `n_estimators=600`, `learning_rate=0.03`, `max_depth=10` 등 과적합을 방지하고 모델 안정성을 극대화하는 최적의 파라미터 조합을 도출했습니다.

### 5단계: 임계값(Threshold) 최적화
머신러닝이 출력하는 '악성일 확률'을 바탕으로 최종 판정을 내리는 기준선(Threshold)을 조율했습니다.
*   기본값인 0.5를 사용할 경우 정상 파일의 17%를 악성으로 오탐하는 치명적인 문제가 있었습니다. 
*   이를 해결하기 위해 Threshold를 **0.85**로 상향 조정했습니다. 그 결과 정상 파일 오탐률(FPR)이 17%에서 8.6% 수준으로 크게 감소하면서도 악성 탐지율(악성 Recall)은 0.95 이상으로 방어할 수 있었습니다.

### 6단계: 최종 학습 및 성능 평가 (Final Evaluation)
모든 설계 결정(피처 50개 + SMOTE 1:4 + 튜닝된 LightGBM + Threshold 0.85)을 조합하여, 격리해둔 20%의 Test 데이터셋으로 최종 평가를 단 1회 수행했습니다.
*   **최종 모델 성능:** 종합 지표인 Balanced Accuracy 0.93, 악성 파일을 성공적으로 탐지한 **악성 Recall 0.95**, 오탐률(FPR)은 단 8.6%를 기록하며 우수한 탐지 성능을 입증했습니다.
*   이 모든 요소는 `models/lightgbm_final.pkl`이라는 하나의 번들 파일로 저장되어 실환경에 배포할 수 있는 산출물로 완성되었습니다.

### 7단계: 모델 해석(Explainability) 및 데모 도구 개발
모델이 왜 이런 결정을 내렸는지 도메인 지식과 결합하여 해석하고 실제 사용 가능한 툴로 패키징했습니다.
*   **모델 의사결정 해석 (SHAP):** 분석 결과, 모델은 메모리 권한 조작 및 동적 로딩과 같은 '악성 API의 존재(VirtualAlloc 등)' 신호뿐만 아니라, C 런타임 종료 함수인 `_cexit`이나 GUI API와 같은 '정상 프로그램 고유 패턴의 부재'를 동시에 강력한 지표로 학습했다는 점을 파악했습니다.
*   **데모 도구 배포:** 실제 분석 환경에서 이 모델을 사용할 수 있도록 Flask 기반의 웹 인터페이스와 대량 폴더 단위 일괄 예측 도구(`batch_predict.py`)를 개발하여 `tool/LightGBM/` 디렉터리에 제공하고 있습니다.
